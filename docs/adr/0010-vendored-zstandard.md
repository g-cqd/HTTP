# ADR 0010 — Zstandard is the vendored libzstd, on every build

- **Status:** Accepted
- **Context date:** 2026-11-26

## Context

The `zstd` content coding (RFC 8878, RFC 9659) linked the system libzstd through the `CZstd` shim behind the
opt-in `Zstd` trait. That had three costs: the default build could not offer zstd at all; a build that enabled it
depended on a package manager's library (Homebrew's on macOS, whose deployment target is newer than ours, and
`libzstd-dev` on Linux); and the shim bridged only one-shot `ZSTD_compress`, so a streamed response that negotiated
`zstd` was served uncoded. apple-docs, which depends on this package, had meanwhile vendored libzstd's decoder for
its own corpus blobs.

An in-house Zstandard codec was prototyped in aemi (`AemiCompression`) and measured against libzstd 1.5.7 in the
same process: 0.87–0.99x its encode speed and 0.83–0.91x its decode speed, with only levels 1–4 and none of
libzstd's years of fuzzing. It was abandoned: no other package in the family needs zstd, and it was not better.

## Decision

1. **Vendor libzstd 1.5.7** as the `CHTTPZstd` target: upstream's single-file library (`vendor/zstd.c`, compressor
   and decompressor, no legacy formats, no assembly) with its headers and BSD license, generated by
   `scripts/vendor-zstd.sh` from the release tarball verified against its published SHA-256. The files are never
   edited by hand.
2. **Hide it.** `chttpzstd.c` includes `vendor/zstd.c` with every libzstd symbol hidden and exposes a small
   `chttpzstd_` surface, so this copy cannot interpose, or be interposed by, a system libzstd another library loads
   into the same process (libcurl does on Linux).
3. **`HTTPZstd`** is the Swift face, a product of its own so consumers (apple-docs) share this one copy:
   `Zstd.compress`, a bounded `Zstd.decompress` (output limit, and a window limit derived from it: at least RFC
   9659's 8 MiB, at most 128 MiB, refused before allocation), and `ZstdCompressionStream`. Contexts are pooled
   (four per level), because a level-3 context holds about 3.5 MiB of tables that a fresh one must clear.
4. **One encoder for both paths.** Compression always runs as a stream that writes no content size, so a body coded
   whole and coded in chunks is the same frame byte for byte (pinned by tests at chunk sizes from 1 octet up).
   `ZstdEncoder` is therefore a `StreamingContentEncoder`, in `defaultEncoders` on every build, at level 3
   (libzstd's default; level 9's 17 MiB per concurrent stream was too much for a server).
5. The `Zstd` trait, `CZstd` and `HTTP_ZSTD_PREFIX` are removed.

## Consequences

- zstd is offered (br > zstd > gzip) and streamed on every build, with no system dependency.
- The default level drops from 9 to 3: somewhat larger zstd bodies, about a fifth of the memory and less CPU per
  response.
- Upgrading libzstd is `scripts/vendor-zstd.sh <version> <sha256>`, reviewed as a vendor bump.
- Inbound `zstd` request bodies (`DecompressionMiddleware`) remain a separate decision; `Zstd.decompress` is the
  bounded primitive it would use.
